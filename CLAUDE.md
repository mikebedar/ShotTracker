# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ShotTracker is a SwiftUI + SwiftData iOS 27 app (deployment target 27.0 for the app, the widget and both test targets; built with Xcode 27.1) for tracking medication doses: schedules ("regimens"), reminders/notifications, and a history of taken/skipped/snoozed doses. There is no `Package.swift` and no CocoaPods: native frameworks (`SwiftUI`, `SwiftData`, `Observation`, `UserNotifications`) inside `ShotTracker.xcodeproj`, plus one Swift package, **Atelier** (Mike's design system, added in the project; see UI: Atelier below). Command-line builds pass `-scmProvider system` so git fetches Atelier with the SSH key.

## Commands

Build and test via `xcodebuild` (no Package.swift, so `swift build`/`swift test` don't apply):

```sh
# Build (an iOS 27 simulator; "iPhone 17" exists under the iOS 27.0 runtime on this machine)
xcodebuild build -project ShotTracker.xcodeproj -scheme ShotTracker -destination 'platform=iOS Simulator,name=iPhone 17,OS=27.0'

# Run all unit tests
xcodebuild test -project ShotTracker.xcodeproj -scheme ShotTracker -destination 'platform=iOS Simulator,name=iPhone 17,OS=27.0' \
  -only-testing:ShotTrackerTests

# Run a single test suite (Swift Testing syntax)
xcodebuild test -project ShotTracker.xcodeproj -scheme ShotTracker -destination 'platform=iOS Simulator,name=iPhone 17,OS=27.0' \
  -only-testing:ShotTrackerTests/TodayBucketingTests

# UI tests (headless; skip the launch-performance test, it relaunches the app 5×)
xcodebuild test -project ShotTracker.xcodeproj -scheme ShotTracker -destination 'platform=iOS Simulator,name=iPhone 17,OS=27.0' \
  -only-testing:ShotTrackerUITests -skip-testing:ShotTrackerUITests/ShotTrackerUITests/testLaunchPerformance

# Screenshot tour: walks every screen over the demo data. The test drops `<name>.request`
# files in TEST_RUNNER_SCREENSHOT_DIR and waits for `<name>.png`; a host loop answers each
# with `xcrun simctl io <udid> screenshot` (XCUITest's own screenshots come back rotated
# and cropped on the iOS 27 simulator). Skipped when the variable isn't set.
TEST_RUNNER_SCREENSHOT_DIR=/tmp/shots xcodebuild test … -only-testing:ShotTrackerUITests/ScreenshotTourUITests
# (testDecisionsTour: the two-zone Today, a snoozed dose, home-zone note/editor/picker, Settings → Time Zones)

# Background refresh on a DEVICE: run the Debug app (not -uiTesting, so it submits its request),
# pause in Xcode's debugger, then
e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"bedar.net.ShotTracker.refresh"]
# and continue. The iOS 27 SIMULATOR refuses submitTaskRequest ("BGTaskScheduler is not available
# on this platform"), so there that command logs "No task request … has been scheduled" (tried
# 2026-10-23 with `xcrun lldb -p <pid>`). On a simulator, run the same handler once after launch:
xcrun simctl launch <udid> bedar.net.ShotTracker -runBackgroundRefresh
# Either way, read the `background` log category (info level):
xcrun simctl spawn <udid> log show --last 5m --info --predicate 'subsystem == "bedar.net.ShotTracker" AND category == "background"'
```

**Launch arguments (Debug builds only, `Support/LaunchOptions.swift`)**: `-atelierTheme <id>` (start on an Atelier theme, never stored: `shottracker`, `system`, `warm`, `studio`, `contrast`, or `canary`, which paints everything the theme reaches in loud colours), `-toastPlacement top` (toasts at the top instead of above the tab bar), `-uiTesting` (in-memory store, a throwaway `UserDefaults` suite for preferences and `@AppStorage`, no notification-permission prompt), `-uiTestStubNetwork` (`Support/StubURLProtocol.swift` answers RxTerms/openFDA: any term → an oral pill with two strengths and an injectable; `zzz` → no matches; `offline` → a connection error), `-seedDemoData` (`Support/DemoData.swift`: one medication per regimen kind, today's doses spread over the Today buckets relative to the launch time, a week of history incl. one of yesterday's Metformin doses snoozed and taken 15 min late; only into an empty store), `-deviceTimeZone <id>` (the device "is" in that zone: sets `TZ` + `tzset` + `NSTimeZone.resetSystemTimeZone()` and `NSTimeZone.default` at launch — on iOS 27 `NSTimeZone.default` alone moves `Calendar.current` but not `TimeZone.current`/`.autoupdatingCurrent`, which formatters use) and `-demoHomeTimeZone <id>` (the zone the demo schedules are written in; their times and "today" are computed on that clock so the buckets don't move), `-runBackgroundRefresh` (run the background-refresh handler once after bootstrap), `-demoTrip` (with the two zone flags: the demo is planned on its home clocks as if the phone had just landed, plus "Malarone" — keep 20 hours, its next dose held back an hour — and "Doxycycline" — set up in Dubai, move an open dose now — `launchedForTesting(seedDemoData: true, twoZones: true, trip: true)`); Every UI test launches through `XCUIApplication.launchedForTesting(seedDemoData:)` (`ShotTrackerUITests/UITestSupport.swift`), so tests never depend on each other or on a previous run, and none touch the network.

Unit tests (`ShotTrackerTests`, 188 tests; UI: 27 plus four screenshot tours, skipped without `SCREENSHOT_DIR`) use Swift Testing (`import Testing`, `@Test`, `#expect`). ## Architecture

**Layering**: SwiftUI views (`Features/`) → `AppDependencies` (composition root) → stateless service/engine objects → `Repository` enums → SwiftData `ModelContext`.

- **`App/AppDependencies.swift`** is the composition root. It's a `@MainActor @Observable` singleton (`AppDependencies.shared`, injected via `EnvironmentValues.appDependencies`) holding the engine/service instances (`DoseScheduleEngine`, `DoseStatusEvaluator`, `MedicationLookupService`, `NotificationScheduler`, `AppPreferencesStore`). Views call: `bootstrapIfNeeded` (once; seeds demo data under `-seedDemoData`), `refreshSchedules` (regenerate the materialized window → reschedule notifications → widget), `sceneBecameActive` (`AppRootView` on every foreground: the day may have changed, the 64-request notification budget needs topping up, permission may have changed), `preferencesChanged` (Settings, debounced 400 ms: routine windows and the reminder lead change generation, the global toggles change what's pending), `recordDoseAction` (repository mutation + event, then a full `refreshSchedules` — a taken dose can re-anchor a rolling schedule, which used to wait for the next refresh) and `logRefill`. Notification reschedules are chained one at a time (`rescheduleAll` clears and re-adds everything; two overlapping runs could lose reminders). Failures are logged with `Logger` (subsystem `bedar.net.ShotTracker`), never silently swallowed. There is no iCloud sync (the old "Enable iCloud Sync" toggle stored a flag nothing read; it and `SyncSettingsStore` were removed). Read this file first to see how the pieces fit together.

- **Persistence (`Persistence/`)**: SwiftData models live in `Models/MedicationModels.swift`: `Medication` → has-many `MedicationRegimen` (versioned schedule definitions, cascade-deleted) → has-many `RegimenPhase` (for `.phased` regimens) and `ReminderPolicy`. `Medication` also has-many `ScheduledDose` (a generated occurrence) and `DoseEvent` (a logged action against a dose). Access to SwiftData is never done directly from views/services — it goes through `Repositories/MedicationRepository` and `Repositories/DoseRepository`, both `@MainActor` enums of static functions taking a `ModelContext` explicitly.

- **Scheduling (`Services/Scheduling/`)**: `DoseScheduleEngine.generateOccurrences` is the core algorithm — given a `MedicationRegimen` and a date range, it walks each day, resolves the active `RegimenPhase` (if any) for that day offset from the regimen's anchor date, checks the `RecurrenceRule` (`daily`/`intervalDays`/`weekly`/`monthly`/`cycle`/`phased`) via `matches(rule:on:...)`, and resolves each `DailyTiming` into concrete times. Each occurrence gets a stable, idempotent `occurrenceKey` (`"{medicationID}-v{regimenVersion}-{yyyyMMddHHmm}-{timingLabel}"`, from the window-start time, built by `DoseScheduleEngine.occurrenceKey` from the **regimen's** calendar — a formatter in the device's zone changed every key when the user travelled). `timingLabel` is an identifier, not display text: `DailyTiming.slotLabel` is `"morning"`, `"before-bed"`, or `"at-0902"` for a specific time (it used to be the localized title, which carried `ClockTime.displayText`'s UTC-offset bug: "4:02 Am" for a 9:02 dose). Display goes through `SlotTitle` / `ScheduledDose.slotTitle` ("Morning", "Before bed", or the dose's own time) — never `.capitalized` a label. Each occurrence and `ScheduledDose` also carries `timingID` (the `DailyTiming.id`; optional, nil on old rows) — the slot's identity across key changes. `DoseStatusEvaluator` derives a dose's live `DoseStatus` (upcoming/due/overdue/takenOnTime/takenLate/skipped/snoozed). `.phased` regimens dose only inside their phases (after the last finite phase, nothing — a finished taper used to continue daily forever), and a phase's interval counts from the phase's first day; phases are edited in `EditMedicationView` (title, every day / every N days, length or "continue with no end" on the last; phase timings stay empty so all phases use the regimen's times).

- **Flexible timing (windows vs. points)**: "when to take a dose" is a **window**, not an instant. `.exactTime` timings are precise points (with `graceWindowMinutes` slack, as before); every named slot (`.morning`/`.noon`/`.evening`/`.night`/`.bedtime`) is a `DoseWindow` (a start–end `ClockTime` range) — from `AppPreferences.defaultSlotWindows` (globally editable in Settings' "Routine Windows") unless a `DailyTiming.customWindow` overrides it per-med. The engine resolves each timing to `(scheduledAt = window start, windowEndAt, reminderAt)`; `ScheduledDose` stores `windowEndAt`/`reminderAt` (both optional → nil = a precise dose that falls back to `scheduledAt + grace` via the computed `windowEnd`). `DoseStatusEvaluator` is window-aware: `upcoming` before the window opens, **`due` throughout** it, `overdue` only after it closes; taking a dose any time up to the window close — including early — is `takenOnTime`. So a "Morning" med (6am–noon) taken at 10am reads Due/on-time, not overdue. Reminders fire near a window's *close* (`reminderAt = end − AppPreferences.windowReminderLeadMinutes`, default 60), and `NotificationScheduler` bases escalation on `reminderAt ?? scheduledAt`. `DoseCard.isActionable` is `!isResolved` (Take/Snooze/Skip on any non-taken today dose, including an upcoming later-today one — logging a dose is never blocked by timing). `DoseWindowStatusTests`/`DoseWindowEngineTests` cover this.

- **Missed-dose policy / rolling schedules (`Services/Scheduling/DoseRescheduling.swift`)**: each `MedicationRegimen` carries a `MissedDosePolicy` (`keepToSchedule`/`skipIfLate`/`rescheduleFromLastDose`, defaulted by kind — injection→reschedule, oral→keep). For `.rescheduleFromLastDose`, `DoseRescheduling.engineInputs` re-anchors generation to the **last actual dose** (`Medication.lastAdministeredAt` = latest `completedAt` among taken doses) and generates by pure interval addition (`nominalIntervalComponents`) rather than the calendar matcher — so a weekly injection taken a day late pushes the whole future series out to follow the real dose, instead of staying pinned to its original weekday. The engine's `generateOccurrences` takes `anchorOverride`/`rollingInterval`/`notBefore` to support this (`notBefore` excludes the just-taken slot so re-anchoring never fabricates a duplicate). On the anchor day itself, a rolling regimen still generates the slots that come after the one the last dose filled (`RollingAnchorSlot`, matched by `timingID` then label) — taking the morning dose of a twice-daily injection used to erase that evening's dose. **Fixed policies also carry a `notBefore` floor** at the regimen version's creation day (`DoseRescheduling.fixedGenerationFloor`; the old "plus one day if a dose was completed that day" is gone — `DoseReconciliation` handles the creation day slot by slot): a regimen edit bumps the version, and without the floor, regenerating the materialization window's 7-day lookback under the new version's keys fabricated a week of phantom "overdue" doses (`RegimenEditRegressionTests` covers this, including that pre-fix phantom rows self-heal via the normal untouched-row prune on the next refresh). Because of the floor, tests that build regimens with fixed dates must pin `createdAt` (usually to the anchor) — the default `.now` makes generation start "today," which drifts as real time advances. Both scheduling tiers call `engineInputs` so materialized and forecast projections agree. A re-anchor does **not** bump the regimen version — the `occurrenceKey`'s date component shifts, which `refreshSchedules`'s diff handles (old-grid future rows deleted, new-grid inserted, notifications rescheduled). `.cycle`/`.phased` don't roll (no single interval → fall back to fixed). A minimum-interval guard (`DoseRescheduling.minimumIntervalWarning`, default 3 days for weekly injections) warns — non-blocking — when logging a rolling dose too soon after the previous one; the Take handlers in `TodayView`/`MedicationScheduledDosesView` present it before `recordDoseAction`. `MedicationArchiveTests`/`DoseReschedulingTests`/`MissedDoseSchedulingIntegrationTests` cover this.

- **Two-tier occurrences (materialized vs. forecasted)**: only a rolling window (`DoseRepository.materializationLookbackDays = 7` … `materializationLookaheadDays = 90`) of occurrences is generated as `ScheduledDose` rows. `DoseRepository.refreshSchedules` applies the plan from `Services/Scheduling/DoseReconciliation.swift` (pure, unit-tested): match by key; else by slot on the same day (`timingID`, else label, else instant) — an untouched or snoozed row is re-keyed in place, a completed row absorbs the new occurrence (so moving a routine window, travelling, an exact-time label change or a version bump never produces a second "due" copy of a dose already taken); else a completed row the new grid has no slot for still uses up one of that day's occurrences (a once-a-day med edited after today's dose doesn't ask for another today). Pruning deletes an unmatched **untouched** row inside the generated range only if it belongs to the current version or its window hasn't closed; closed windows of older versions and everything outside the range are **kept** — they are the record of missed doses (the old rule deleted every untouched row once it left the 7-day lookback, so 30-day adherence only ever saw a week of misses). This is the **actionable** tier: only these rows carry mutable state (status, snooze, completion, supply decrement, notifications). Everything beyond the window is served **on the fly** by `DoseForecastService` (RFC-5545-style lazy expansion — never persisted, always `.upcoming`), so the calendar/"Coming Up" can look arbitrarily far ahead without storing rows forever. Both tiers flow through the UI as `DisplayDoseItem` (wraps a `ScheduledDose` + its `Medication` + an `isForecasted` flag; forecasted items render dimmed and carry the medication alongside rather than via `dose.medication`, which is deliberately left unset on transient doses). The calendar caps paging at ±2 years (`DoseCalendarView.availableDateRange`). When adding a display path that shows future doses, feed it through `DisplayDoseItem`/`DoseForecastService` — don't assume persisted rows exist past +90 days.

- **Time zones: home clock, both times away from it (decided 2026-10-23; named slots now follow the device, see the next item)**: a regimen keeps the zone it was created in (`MedicationRegimen.timeZoneIdentifier`, `homeTimeZone`); generation, occurrence keys and windows are on that clock, and every dose fires at the true instant. Wherever a dose time is shown — `DoseCard` (timing line, footers), `SimpleDoseRow` (calendar day list), `ComingUpRow`, `MedicationScheduledDosesView`, the medication list's next dose, `DoseEventRow` (History), the CSV, notification text and the widget — it goes through `ZonedTimeFormatter` (`Shared/Widget/ZonedTimeFormatter.swift`, compiled into the widget too via an explicit build-file reference like the snapshot): "8:00 AM" when the clocks agree, else **"8:00 AM home · 2:00 PM here"** (the home part adds its weekday when it falls on another day, "11:00 PM Mon home · 5:00 AM here"; `dateTime` for dated rows; `spokenTime` for VoiceOver, "8:00 AM home time, 2:00 PM local time"; `timeWithZoneNames` for the CSV, "8:00 AM EDT (2:00 PM GMT+2 local)"). "Differs" is a different UTC offset at that instant, not a different identifier (Detroit vs New York reads as one time; New York vs Paris shows five hours in the DST gap weeks). A dose's home zone is its regimen *version's* (`ScheduledDose.homeTimeZone` / `Medication.homeTimeZone(forVersion:)`; forecast doses carry no medication, so rows ask the medication passed in). `NotificationScheduler.trigger(for:)` pins calendar triggers to their instant (components carry the time zone). `MedicationDetailView` shows a "Scheduled on New York time" note only away from home; `EditMedicationView` has a "Home time zone" row (→ `TimeZonePickerView`, searchable, device zone first) and, away from home, "Use This Device's Time Zone"; `MedicationDraft.homeTimeZoneIdentifier` starts from the regimen (an edit made while travelling used to re-home the schedule silently) and a change is a schedule change → a new regimen version, which re-anchors future doses through the normal reconciliation (today's taken dose absorbs the new slot; history keeps its old zone). Settings → Time Zones names the device's zone and explains home zones. `TimeZoneDisplayTests` (fixed zones, DST edges, day crossing, re-homing) and `DecisionsUITests` (two-zone launch) cover it.

- **Named slots follow the device (decided 2026-10-23, branch `travel`)**: "If I'm from NY and I travel to Paris I'd like it to say 'Morning (Paris)', 'Home: Night'." Each regimen has a "When travelling" setting (`MedicationRegimen.travelPolicyRaw`, `TravelTimePolicy` `.followsMe`/`.staysOnHome`; nil = by timing kind: named slots follow, specific times stay home — every regimen from before this reads nil, so no data migration beyond the new optional column). It is part of the schedule (`MedicationDraft.scheduleDiffers` compares the *effective* policy per timing, so picking the default explicitly isn't a change) and sits under the Home time zone row in Edit (a mix of slots and specific times offers "Automatic"). **Generation** (`DoseScheduleEngine.generateOccurrences`): when the device zone (`DeviceClock`: `.system` = `TimeZone.current`, `.fixed(zone)`, `.atHome`; tests that predate travel use `.atHome` through `TestSupport.engine()`/`refresh(device:)`) isn't the home zone, follows-me timings are generated on a device-zone calendar on the same calendar dates (the anchor's home date; a rolling schedule's local day of the last dose; the fixed-policy floor is now a *day* read on each clock, `EngineInputs.floorDay`, not an instant), their keys end in `@Europe/Paris` and the rows carry `ScheduledDose.clockTimeZoneIdentifier` (nil = home). Both tiers go through `generateOccurrences(for: medication, regimen:…)`. **Reconciliation** (`DoseReconciliation`) matches step 2 by slot on the same **local day**, each side's date read on its own clock: a taken/skipped row absorbs the new occurrence (no second Morning that day), a row open right now stays on its clock until it closes, and nothing moves into a window already closed on the new clock (an evening dose due when the phone switches mid-flight stays on New York's clock until it closes; a missed one stays missed unless its slot is still ahead on the new clock — flying west); that's the default "Finish it on the old clock", see Travel options for the others. Re-plans happen on launch, foreground, `NSSystemTimeZoneDidChange`/significant time change and the background refresh, as before. Prune range starts at the later of the two clocks' midnights. **Labels** (`Shared/Widget/SlotClockLabel.swift`, compiled into the widget too; app side `Support/DoseClockText.swift`): at home "Morning" as before; away, a follows-me slot reads "Morning (Paris)" + "Home: Night · 2:00 AM", one kept home "Morning (home)" + "Here: Afternoon · 2:00 PM" (a dose on a third clock, e.g. a Paris dose seen back home, "Morning (Paris)" + "Home: …"). "Away" = different UTC offset at the window's middle; the other clock's part of day is read at the window's middle from the routine windows (`AppPreferences.dayParts`: morning/noon/evening/night windows, nearest middle wins an overlap, else night/morning/afternoon/evening; `EnvironmentValues.dayParts` set in `AppRootView`), the place from the zone identifier ("Buenos Aires"), else its abbreviation. Times of a slot read on its own clock; footers/snooze use `DoseClockText.times` (local only for a follows-me slot). Specific times keep "8:00 AM home · 2:00 PM here". Spoken: "Morning in Paris, anytime by 12:00 PM; at home it's night, by 6:00 AM" / "Morning, home time, …; here it's afternoon, …". Surfaces: `DoseCard` (timing line + detail line), `SimpleDoseRow`, `ComingUpRow`, `MedicationScheduledDosesView`, the medication list, `DoseEventRow` (the slot as it read where it was taken, "Morning (Paris) · Home: Night", and the logged time on that clock: `DoseEvent.timeZoneIdentifier`, recorded by `applyAction(timeZone:)`; "Oct 24 at 2:05 AM home · 8:05 AM Paris" once home), the CSV (new **Time Zone** column; Date/Time on the clock the action was logged on; Detail "Scheduled 2026-10-24 6:00 AM GMT+2 (Morning (Paris); Home: Night · 12:00 AM EDT)"), notifications ("Morning dose (Paris) · Home: Night · take by 12:00 PM." / "Morning dose (home) · Here: Afternoon · take by 12:00 PM home · 6:00 PM here."), the widget (`WidgetDoseItem.slotTitle`/`clockTimeZoneIdentifier`, `TodayWidgetSnapshot.dayParts`, all optional for old snapshots: "Morning (Paris) · by 12:00 PM · Home: Night", the small widget adds `detailText`). Adherence needs nothing: a follows-me dose's window *is* the local one, so a dose taken in the Paris morning is on time. `MedicationDetailView`'s away note and Settings → Time Zones explain both. Demo: with `-deviceTimeZone` ≠ `-demoHomeTimeZone`, Metformin's custom window is written on the device clock and a kept-home "Levothyroxine" (morning, window open now on the home clock) is added. `TravelSlotTests` (NY→Paris→NY, DST weeks both springs and autumns, the mid-day and overnight flights, flying west, exact times unaffected, override both ways, the default for old regimens, the draft, labels and day parts, re-planned reminders, the widget item/timeline, on-time adherence + history + CSV) and `DecisionsUITests.testAwayFromHomeSlotsFollowTheDevice` cover it.

- **Travel options (decided 2026-10-23, branch `travel-options`)**: "these questions should be optional behavior — we need to be clear when people set up a schedule what is happening, and let them control it." Edit has a **When you travel** block after Schedule (home time zone row, then three inline choices, each option with its one-line explanation, then a live example): **Clock** (`TravelTimePolicy`: "Follows me" / "Stays on home time", "Automatic" only for a mix of named slots and specific times), **Long trips & date lines** (`TravelSpacing`: "Count by calendar day" / "Keep at least N hours between doses", N in a stepper) and **Landing during a dose** (`TravelLanding`: "Finish it on the old clock" / "Move it to the new clock now"); the last two are disabled with a footer when nothing follows the device. Stored on `MedicationRegimen` as optional `travelSpacingRaw` / `travelMinimumHours` / `travelLandingRaw` (nil = calendar day / the recurrence's default N / finish: every regimen from before reads as the old behaviour); `travelSettings` bundles them (`TravelSettings`, also the draft's). Part of the schedule: `MedicationDraft.scheduleDiffers` compares the effective values (N only in hours mode), so a change is a new regimen version. **Defaults for a new medication** (`TravelSettings.suggested`, re-applied on kind / timings / "Break through Focus" changes until the user touches a travel choice, like the missed-dose policy): injections and time-sensitive ones (Focus: Always) stay on home time and keep at least N hours; all-specific-time schedules keep N hours (and stay home by timing); everything else follows by timing kind and counts by calendar day; landing always finishes on the old clock. **N** defaults to the usual gap minus four hours (`TravelSettings.defaultMinimumHours`: daily 20, every 3 days 68, weekly 164, Mon+Thu 68, monthly 28 days − 4 h). **Reconciliation** (`DoseReconciliation.plan(rules:)`, `TravelRules(regimen:)`; the doc comment is the spec): *finish* — a row whose window is open right now stays on its clock until it closes (this now also holds flying west: before, an open Paris morning jumped at once to New York's later morning), nothing moves into a window already closed on the new clock; *move now* — an open or not-yet-open row moves to the new clock's same-day slot at once, even into a closed window (overdue there, "Morning (Paris)", and superseded once it is an earlier local day); a row already missed stays. *Hours mode* (follows-me slots only): L = the slot's latest taken dose (`Row.completedAt`/`isTaken`, any version); an occurrence on another clock than L's row whose window ends after L is judged by hours — ends within N h → **covered** (no dose; its untouched row goes; a same-day old-clock row is kept as history, held when open now or when the covered window has closed, else deleted), opens before L + N → **held** (`spacingHoldHours` = N, start = L + N, reminder no earlier, same key so Undo restores it), and rows completed at or before L neither absorb it (step 2) nor use up its day (step 3). Same clock as L (at home, or once a dose was taken on the new clock) → calendar rules, so nothing changes without travel. Consequences: NY → Paris, by day the next morning is 6:00 Paris (16 h later), by hours 10:00 (20 h); Tokyo → NY (a date lived twice) the NY morning is covered at N = 20 and offered at N = 10; LA → Sydney (a date skipped) by hours the Sydney morning an hour after a dose taken on the plane is covered; a minimum longer than the window allows covers that day (N = 23 from NY to Paris: no Oct 24 morning). `ScheduledDose.spacingHoldHours` (optional) drives `DoseCard`'s "Opens 10:00 AM, 20 hours after your last dose" (also spoken); notifications and the widget read the held `scheduledAt`/`reminderAt`. **One pure planner**: `DoseReconciliation.refreshPlan` (generation via `DoseScheduleEngine.generateOccurrences(regimen:medicationID:inputs:)`, `DoseRescheduling.engineInputs(regimen:lastTaken:)` on plain `LastTakenDose`) is what `DoseRepository.refreshSchedules` applies to the store and `TripSimulation` applies to plain values. **Live example** (`Services/Scheduling/TravelExample.swift`): `TravelExample.make(schedule:destination:preferences:from:)` simulates, with the first timing that follows (else the first): the long flight (take the next dose two hours into its window, leave an hour later, fly |difference| + 2 h, 3–15, re-plan on the destination clock → the next dose, its clock, hours since, held or not, and whether the landing day's still-open window gets a dose) and landing during a dose (switch halfway through the window → kept / moved / late, and where a kept one goes once it closes). Templates word the facts ("If you fly from New York to Paris (6 hours ahead):", "Morning dose: anytime 6:00 AM–12:00 PM Paris time (12:00 AM–6:00 AM at home).", "… The next Morning dose opens the next day at 10:00 AM Paris time instead of 6:00 AM: 20 hours after the last."); the clock line is the departure date on the destination clock; phased schedules simulate as daily. Destinations: `TravelDestinations` (20 cities, searchable `TravelDestinationPickerView`; default Paris from the Americas, Tokyo from Europe/Africa, New York from Asia/Pacific). **How this schedule works** (`ScheduleSummary`, `Inputs(regimen:)` / `MedicationDraft.summaryInputs`; `ScheduleSummaryView`): When (cadence + windows / grace), If you're late (per missed-dose policy, rolling interval + heads-up), Reminders and snooze (lead, follow-ups as the planner fires them, snooze length or off), When you travel (the three choices). Shown by Save as a confirmation sheet (`ScheduleConfirmationView`: Keep Editing / Save) when the schedule is new or changed (other edits save at once), and as a section on `MedicationDetailView` after Scheduled doses / History (above Supply it pushed "Log refill" and the links below the fold, which three UI tests caught). `TravelOptionsTests`, `TravelExampleTests` (incl. "the example is what the store does") and `TravelOptionsUITests` cover it.

- **Background refresh (decided 2026-10-23, `Services/Background/BackgroundRefresh.swift`)**: a `BGAppRefreshTask` (`bedar.net.ShotTracker.refresh`, in `ShotTracker/Info.plist` `BGTaskSchedulerPermittedIdentifiers` with `UIBackgroundModes` = `fetch`; the app target now has a partial physical Info.plist merged with the generated one, excluded from Copy Resources by a sync-group exception) registered through SwiftUI's `.backgroundTask(.appRefresh(…))` in `ShotTrackerApp`. Requests are submitted at bootstrap and when the scene backgrounds (not under `-uiTesting`; the iOS 27 simulator refuses them, see Commands for `-runBackgroundRefresh`). - **Notifications (`Services/Notifications/`)**: `NotificationPlanner` (pure) decides what should be pending; `NotificationScheduler.plan` computes the budgeted plan from the store (pure apart from the fetch) and `rescheduleAll` clears and adds it. - **State flow for a dose action**: a view calls `AppDependencies.recordDoseAction(_:dose:context:)` → `DoseRepository.applyAction` mutates the `ScheduledDose` (status/completedAt/snoozedUntil/snoozeOffsetMinutes), appends a `DoseEvent`, saves the context → `AppDependencies.refreshSchedules` regenerates (rolling re-anchor), reschedules notifications and republishes the widget. When editing this flow, all three steps (repository mutation, event log, notification reschedule) need to stay together. **Snooze** only applies once a dose is due (`DoseActions.canSnooze`: due/overdue/snoozed, and the policy's `allowSnooze`); `applyAction` refuses an upcoming one (no event) and `DoseActionBar` hides the button (`onSnooze: nil`). `MedicationScheduledDosesView` offers actions only on due/overdue/snoozed doses and the next upcoming one (early doses stay possible); the rest of the 90 days is a preview.

- **Snooze tracks an offset (decided 2026-10-23)**: a snooze shifts only that dose, by the snooze length (the policy's `defaultSnoozeMinutes`, 20). `ScheduledDose.snoozeOffsetMinutes` (optional, nil = 0; `snoozeOffset`) is the cumulative total; `ScheduledDose.deadline` = original `windowEnd` + offset is when the dose turns **overdue** (`DoseStatusEvaluator`: snoozed while `snoozedUntil` is ahead, upcoming before the window opens, due until the deadline). **On time vs late is judged against the original window** (`completionStatus` uses `windowEnd`; `ScheduledDose.minutesLate`). The old rule moved both window bounds to the snooze end, so a morning dose snoozed at 10:00 counted on time until ~16:20. Snoozing again while a snooze runs extends it from its end (two taps = 40 min, never a shorter real delay than the offset). The reminder fires at `snoozedUntil` (escalations follow it); notification text uses the deadline ("Morning dose · snoozed 20 min · take by 12:20 PM."). Each `DoseEvent` records `snoozeMinutes` (what that snooze added), `snoozeOffsetMinutes` (the dose's total once it applied) and, for a take, `minutesLate` — all optional, nil on old rows. **Undo** (`.pending`) of a snooze takes exactly that snooze's minutes back (and the time it added to a running earlier snooze); a pre-tracking snooze event (no minutes) just ends; undoing a take/skip keeps earlier snoozes. `DoseCard` shows a snooze footer ("Snoozed 20 min · reminder at 10:20 AM", Undo while the last action is the snooze); its resolved footer adds "· 15 min late · snoozed 20 min". Wording lives in `Support/SnoozeWording.swift`: history/CSV events read "Snoozed 20 min" ("· 40 min in all" after a second), "Taken on time · snoozed 20 min", "Taken 45 min late · snoozed 30 min" (events from before tracking keep "Taken"/"Snoozed"). **Adherence** (`AdherenceStats`): a snoozed-then-taken dose counts as taken; `snoozedCount` (taken after a snooze) and `lateCount` are reported beside the percentage (History shows a "taken after a snooze" tile when > 0). `SnoozeOffsetTests` covers status, deadline, multiple snoozes, undo, notification time, widget parity, wording, adherence and old-row decoding.

- **HealthKit medications (investigated, not built)**: the iOS 26 HealthKit medication APIs (`HKMedicationDoseEvent`, `HKUserAnnotatedMedication`) are **read-only for third-party apps** — every initializer is `NS_UNAVAILABLE` and all properties readonly, so exporting dose logs into Apple Health is not possible. Only a read/import direction (mirroring the user's Health-app med list) is viable if ever wanted.

## Conventions

- Status, frequency, timing, and kind are modeled as exhaustive `String`-backed enums (`DoseStatus`, `DoseActionType`, `ScheduleFrequency`, `TimingAnchorKind`, `MedicationKind`) in `MedicationModels.swift` rather than free-form strings or booleans — extend these enums (and their `title` switch statements) rather than adding parallel flags.
- Colors, spacing, radii, and fonts come from Atelier's tokens (`.padding(.l)`, `Column(spacing: .s)`, `.textRole(…)`, `.foregroundStyle(.contentSecondary)`, `.surface(…)`) or the `Theme` facade (`Support/DesignSystem/`), never hardcoded values or `Color("...")`; status colors come from `DoseStatus.tone` (`.tone(status.tone)`, `Badge(…, tone: status.tone)`) / `themeColor` / `themeSoftColor` only.
- New `Medication`/`ScheduledDose` stored properties must be optional (or have an in-declaration default) — the app relies on SwiftData's automatic lightweight migration with no versioned schema plan, which only handles additive changes. New `@Model` types must also be registered in `MedicationModelContainer.makeSharedContainer()`'s `Schema`.
- Verify any data-model change by launching over a simulator that already has app data (install without uninstalling first) to confirm lightweight migration doesn't crash — not just against a fresh install.
- Repositories are `@MainActor enum`s of `static` functions that take `ModelContext` explicitly as a parameter — there are no repository instances or protocols.
- Regimens are versioned (`MedicationRegimen.version`); schedule changes should create a new version rather than mutating occurrence generation for existing `ScheduledDose`s in place, since `occurrenceKey` embeds the version.

## Motion regression checks

`ShotTracker.xcworkspace` includes the sibling `../Atelier` checkout for validating shared motion changes in the real
app. The `.xcodeproj` continues to use its tagged dependency; opening the workspace does not update that pin.
`MotionFeedbackUITests` runs Take/Undo against fresh in-memory demo data: bottom-toast/tab-bar clearance, a resisted
swipe returning to rest, dismissal without undoing the dose, and successive actions undoing only the latest dose.
Each behavior runs with `system`, `reduced`, and `off` motion; the appearance check covers System/Warm, light/dark.

```sh
xcodebuild test -workspace ShotTracker.xcworkspace -scheme ShotTracker \
  -destination 'platform=iOS Simulator,name=iPhone 18 Pro,OS=27.0' -scmProvider system \
  -parallel-testing-enabled NO -only-testing:ShotTrackerUITests/MotionFeedbackUITests
```

DEBUG launch arguments `-atelierMotion system|reduced|off` and `-atelierAppearance system|light|dark` use transient
Atelier preferences, like `-atelierTheme`. Release builds ignore them. The appearance test optionally writes capture
requests to `TEST_RUNNER_SCREENSHOT_DIR`, using the screenshot tour's host-side `simctl` protocol above. Only that visual test uses
`-uiTestHoldToast` (requires `-uiTesting`) to keep the toast for 120 seconds while the host captures it. Gesture and Undo
behavior tests keep the production timeout. UI-test appearances are never published to the widget's shared preferences.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ShotTracker is a SwiftUI + SwiftData iOS 27 app (deployment target 27.0 for the app, the widget and both test targets; built with Xcode 27.1) for tracking medication doses: schedules ("regimens"), reminders/notifications, and a history of taken/skipped/snoozed doses. There is no external dependency manager (no SPM `Package.swift`, no CocoaPods) — everything is native frameworks (`SwiftUI`, `SwiftData`, `Observation`, `UserNotifications`) inside `ShotTracker.xcodeproj`.

## Commands

Build and test via `xcodebuild` (no Package.swift, so `swift build`/`swift test` don't apply):

```sh
# Build (an iOS 27 simulator; "iPhone 17" exists under the iOS 27.0 runtime on this machine)
xcodebuild build -project ShotTracker.xcodeproj -scheme ShotTracker -destination 'platform=iOS Simulator,name=iPhone 17,OS=27.0'

# Run all unit tests
xcodebuild test -project ShotTracker.xcodeproj -scheme ShotTracker -destination 'platform=iOS Simulator,name=iPhone 17,OS=27.0' \
  -only-testing:ShotTrackerTests

# Run a single test suite (Swift Testing syntax)
xcodebuild test -project ShotTracker.xcodeproj -scheme ShotTracker -destination 'platform=iOS Simulator,name=iPhone 17,OS=27.0' \
  -only-testing:ShotTrackerTests/TodayBucketingTests

# UI tests (headless; skip the launch-performance test, it relaunches the app 5×)
xcodebuild test -project ShotTracker.xcodeproj -scheme ShotTracker -destination 'platform=iOS Simulator,name=iPhone 17,OS=27.0' \
  -only-testing:ShotTrackerUITests -skip-testing:ShotTrackerUITests/ShotTrackerUITests/testLaunchPerformance

# Screenshot tour: walks every screen over the demo data. The test drops `<name>.request`
# files in TEST_RUNNER_SCREENSHOT_DIR and waits for `<name>.png`; a host loop answers each
# with `xcrun simctl io <udid> screenshot` (XCUITest's own screenshots come back rotated
# and cropped on the iOS 27 simulator). Skipped when the variable isn't set.
TEST_RUNNER_SCREENSHOT_DIR=/tmp/shots xcodebuild test … -only-testing:ShotTrackerUITests/ScreenshotTourUITests
```

**Launch arguments (Debug builds only, `Support/LaunchOptions.swift`)**: `-uiTesting` (in-memory store, a throwaway `UserDefaults` suite for preferences and `@AppStorage`, no notification-permission prompt), `-uiTestStubNetwork` (`Support/StubURLProtocol.swift` answers RxTerms/openFDA: any term → an oral pill with two strengths and an injectable; `zzz` → no matches; `offline` → a connection error), `-seedDemoData` (`Support/DemoData.swift`: one medication per regimen kind, today's doses spread over the Today buckets relative to the launch time, a week of history; only into an empty store). Every UI test launches through `XCUIApplication.launchedForTesting(seedDemoData:)` (`ShotTrackerUITests/UITestSupport.swift`), so tests never depend on each other or on a previous run, and none touch the network.

Unit tests (`ShotTrackerTests`, 95 tests) use Swift Testing (`import Testing`, `@Test`, `#expect`). Coverage: Today bucketing and supersession, supply container math and forecasting, dose forecasting, windows/statuses, rescheduling, schedule reconciliation (`ScheduleReconciliationTests`: re-keying, missed-dose retention, rolling multi-dose days, phased regimens, snooze, archive), notifications planning, widget snapshot/relevance, lookup parsing and the search model (over `StubURLProtocol`), drug info, adherence, CSV export, the edit form's change detection (`HealthPassBehaviourTests`). `ShotTrackerTests/TestSupport.swift` has the in-memory context and fixtures; tests that need SwiftData semantics use a real in-memory `ModelContainer`. Keep MainActor-isolated values out of default arguments in test helpers (they're evaluated nonisolated). UI tests (`ShotTrackerUITests`, XCTest/XCUITest): lookup add + delete and lookup failures (stubbed), archive keeps history, edit flow, missed-dose default, dose-row identifiers, and `AppFlowUITests` (every tab opens, Take/Undo and where Snooze appears, refill, minimum-interval warning, calendar keeps taken doses, Settings permission row, phased schedule creation). **Tab bar identifiers are not settable**: on iOS 27 the floating tab bar's buttons report their SF Symbol name as their identifier, and neither `.accessibilityIdentifier` on a `Tab` nor setting it on the `UITabBarItem` or the button views changes that (tried 2026-10-23); `AccessibilityID.*Tab` tag each tab's content, and `XCUIApplication.tab(_:)` finds the button by title. A dose row's `AccessibilityID.scheduledDoseRow(id)` lives on a non-interactive sub-element (`DoseCard`'s header, an inner group in `MedicationScheduledDosesView`), never on a container that also holds `DoseActionBar`, or it overrides the buttons' own identifiers (`DoseRowAccessibilityUITests`). Take/Snooze/Skip/Undo each carry a per-dose identifier.

## Architecture

**Layering**: SwiftUI views (`Features/`) → `AppDependencies` (composition root) → stateless service/engine objects → `Repository` enums → SwiftData `ModelContext`.

- **`App/AppDependencies.swift`** is the composition root. It's a `@MainActor @Observable` singleton (`AppDependencies.shared`, injected via `EnvironmentValues.appDependencies`) holding the engine/service instances (`DoseScheduleEngine`, `DoseStatusEvaluator`, `MedicationLookupService`, `NotificationScheduler`, `AppPreferencesStore`). Views call: `bootstrapIfNeeded` (once; seeds demo data under `-seedDemoData`), `refreshSchedules` (regenerate the materialized window → reschedule notifications → widget), `sceneBecameActive` (`AppRootView` on every foreground: the day may have changed, the 64-request notification budget needs topping up, permission may have changed), `preferencesChanged` (Settings, debounced 400 ms: routine windows and the reminder lead change generation, the global toggles change what's pending), `recordDoseAction` (repository mutation + event, then a full `refreshSchedules` — a taken dose can re-anchor a rolling schedule, which used to wait for the next refresh) and `logRefill`. Notification reschedules are chained one at a time (`rescheduleAll` clears and re-adds everything; two overlapping runs could lose reminders). Failures are logged with `Logger` (subsystem `bedar.net.ShotTracker`), never silently swallowed. There is no iCloud sync (the old "Enable iCloud Sync" toggle stored a flag nothing read; it and `SyncSettingsStore` were removed). Read this file first to see how the pieces fit together.

- **Persistence (`Persistence/`)**: SwiftData models live in `Models/MedicationModels.swift`: `Medication` → has-many `MedicationRegimen` (versioned schedule definitions, cascade-deleted) → has-many `RegimenPhase` (for `.phased` regimens) and `ReminderPolicy`. `Medication` also has-many `ScheduledDose` (a generated occurrence) and `DoseEvent` (a logged action against a dose). Access to SwiftData is never done directly from views/services — it goes through `Repositories/MedicationRepository` and `Repositories/DoseRepository`, both `@MainActor` enums of static functions taking a `ModelContext` explicitly.

- **Scheduling (`Services/Scheduling/`)**: `DoseScheduleEngine.generateOccurrences` is the core algorithm — given a `MedicationRegimen` and a date range, it walks each day, resolves the active `RegimenPhase` (if any) for that day offset from the regimen's anchor date, checks the `RecurrenceRule` (`daily`/`intervalDays`/`weekly`/`monthly`/`cycle`/`phased`) via `matches(rule:on:...)`, and resolves each `DailyTiming` into concrete times. Each occurrence gets a stable, idempotent `occurrenceKey` (`"{medicationID}-v{regimenVersion}-{yyyyMMddHHmm}-{timingLabel}"`, from the window-start time, built by `DoseScheduleEngine.occurrenceKey` from the **regimen's** calendar — a formatter in the device's zone changed every key when the user travelled). `timingLabel` is an identifier, not display text: `DailyTiming.slotLabel` is `"morning"`, `"before-bed"`, or `"at-0902"` for a specific time (it used to be the localized title, which carried `ClockTime.displayText`'s UTC-offset bug: "4:02 Am" for a 9:02 dose). Display goes through `SlotTitle` / `ScheduledDose.slotTitle` ("Morning", "Before bed", or the dose's own time) — never `.capitalized` a label. Each occurrence and `ScheduledDose` also carries `timingID` (the `DailyTiming.id`; optional, nil on old rows) — the slot's identity across key changes. `DoseStatusEvaluator` derives a dose's live `DoseStatus` (upcoming/due/overdue/takenOnTime/takenLate/skipped/snoozed). `.phased` regimens dose only inside their phases (after the last finite phase, nothing — a finished taper used to continue daily forever), and a phase's interval counts from the phase's first day; phases are edited in `EditMedicationView` (title, every day / every N days, length or "continue with no end" on the last; phase timings stay empty so all phases use the regimen's times).

- **Flexible timing (windows vs. points)**: "when to take a dose" is a **window**, not an instant. `.exactTime` timings are precise points (with `graceWindowMinutes` slack, as before); every named slot (`.morning`/`.noon`/`.evening`/`.night`/`.bedtime`) is a `DoseWindow` (a start–end `ClockTime` range) — from `AppPreferences.defaultSlotWindows` (globally editable in Settings' "Routine Windows") unless a `DailyTiming.customWindow` overrides it per-med. The engine resolves each timing to `(scheduledAt = window start, windowEndAt, reminderAt)`; `ScheduledDose` stores `windowEndAt`/`reminderAt` (both optional → nil = a precise dose that falls back to `scheduledAt + grace` via the computed `windowEnd`). `DoseStatusEvaluator` is window-aware: `upcoming` before the window opens, **`due` throughout** it, `overdue` only after it closes; taking a dose any time up to the window close — including early — is `takenOnTime`. So a "Morning" med (6am–noon) taken at 10am reads Due/on-time, not overdue. Reminders fire near a window's *close* (`reminderAt = end − AppPreferences.windowReminderLeadMinutes`, default 60), and `NotificationScheduler` bases escalation on `reminderAt ?? scheduledAt`. `DoseCard.isActionable` is `!isResolved` (Take/Snooze/Skip on any non-taken today dose, including an upcoming later-today one — logging a dose is never blocked by timing). `DoseWindowStatusTests`/`DoseWindowEngineTests` cover this.

- **Missed-dose policy / rolling schedules (`Services/Scheduling/DoseRescheduling.swift`)**: each `MedicationRegimen` carries a `MissedDosePolicy` (`keepToSchedule`/`skipIfLate`/`rescheduleFromLastDose`, defaulted by kind — injection→reschedule, oral→keep). For `.rescheduleFromLastDose`, `DoseRescheduling.engineInputs` re-anchors generation to the **last actual dose** (`Medication.lastAdministeredAt` = latest `completedAt` among taken doses) and generates by pure interval addition (`nominalIntervalComponents`) rather than the calendar matcher — so a weekly injection taken a day late pushes the whole future series out to follow the real dose, instead of staying pinned to its original weekday. The engine's `generateOccurrences` takes `anchorOverride`/`rollingInterval`/`notBefore` to support this (`notBefore` excludes the just-taken slot so re-anchoring never fabricates a duplicate). On the anchor day itself, a rolling regimen still generates the slots that come after the one the last dose filled (`RollingAnchorSlot`, matched by `timingID` then label) — taking the morning dose of a twice-daily injection used to erase that evening's dose. **Fixed policies also carry a `notBefore` floor** at the regimen version's creation day (`DoseRescheduling.fixedGenerationFloor`; the old "plus one day if a dose was completed that day" is gone — `DoseReconciliation` handles the creation day slot by slot): a regimen edit bumps the version, and without the floor, regenerating the materialization window's 7-day lookback under the new version's keys fabricated a week of phantom "overdue" doses (`RegimenEditRegressionTests` covers this, including that pre-fix phantom rows self-heal via the normal untouched-row prune on the next refresh). Because of the floor, tests that build regimens with fixed dates must pin `createdAt` (usually to the anchor) — the default `.now` makes generation start "today," which drifts as real time advances. Both scheduling tiers call `engineInputs` so materialized and forecast projections agree. A re-anchor does **not** bump the regimen version — the `occurrenceKey`'s date component shifts, which `refreshSchedules`'s diff handles (old-grid future rows deleted, new-grid inserted, notifications rescheduled). `.cycle`/`.phased` don't roll (no single interval → fall back to fixed). A minimum-interval guard (`DoseRescheduling.minimumIntervalWarning`, default 3 days for weekly injections) warns — non-blocking — when logging a rolling dose too soon after the previous one; the Take handlers in `TodayView`/`MedicationScheduledDosesView` present it before `recordDoseAction`. `MedicationArchiveTests`/`DoseReschedulingTests`/`MissedDoseSchedulingIntegrationTests` cover this.

- **Two-tier occurrences (materialized vs. forecasted)**: only a rolling window (`DoseRepository.materializationLookbackDays = 7` … `materializationLookaheadDays = 90`) of occurrences is generated as `ScheduledDose` rows. `DoseRepository.refreshSchedules` applies the plan from `Services/Scheduling/DoseReconciliation.swift` (pure, unit-tested): match by key; else by slot on the same day (`timingID`, else label, else instant) — an untouched or snoozed row is re-keyed in place, a completed row absorbs the new occurrence (so moving a routine window, travelling, an exact-time label change or a version bump never produces a second "due" copy of a dose already taken); else a completed row the new grid has no slot for still uses up one of that day's occurrences (a once-a-day med edited after today's dose doesn't ask for another today). Pruning deletes an unmatched **untouched** row inside the generated range only if it belongs to the current version or its window hasn't closed; closed windows of older versions and everything outside the range are **kept** — they are the record of missed doses (the old rule deleted every untouched row once it left the 7-day lookback, so 30-day adherence only ever saw a week of misses). This is the **actionable** tier: only these rows carry mutable state (status, snooze, completion, supply decrement, notifications). Everything beyond the window is served **on the fly** by `DoseForecastService` (RFC-5545-style lazy expansion — never persisted, always `.upcoming`), so the calendar/"Coming Up" can look arbitrarily far ahead without storing rows forever. Both tiers flow through the UI as `DisplayDoseItem` (wraps a `ScheduledDose` + its `Medication` + an `isForecasted` flag; forecasted items render dimmed and carry the medication alongside rather than via `dose.medication`, which is deliberately left unset on transient doses). The calendar caps paging at ±2 years (`DoseCalendarView.availableDateRange`). When adding a display path that shows future doses, feed it through `DisplayDoseItem`/`DoseForecastService` — don't assume persisted rows exist past +90 days.

- **Notifications (`Services/Notifications/`)**: `NotificationPlanner` (pure) decides what should be pending; `NotificationScheduler.rescheduleAll` clears and adds that plan. Dose reminders cover upcoming, due, snoozed **and overdue** doses (overdue ones used to lose their remaining escalations at any reschedule after the window closed), skip superseded and archived ones, and read "Time for Metformin" / "Morning dose · take by 12:00 PM." ("… not logged yet", "… is overdue" for follow-ups). iOS keeps only 64 pending requests and silently drops the rest, so the plan is **budgeted**: refill reminders first (one per medication), then the soonest dose reminders; the app re-plans on every launch, foreground and action, so the window moves forward. Medications whose reminder policy disallows snooze get the `DOSE_REMINDER_NO_SNOOZE` category. `lastPlannedCount`/`lastCandidateCount` say how much the budget deferred. Keep the planner and `DoseStatusEvaluator` in sync when changing dose timing logic.

- **State flow for a dose action**: a view calls `AppDependencies.recordDoseAction(_:dose:context:)` → `DoseRepository.applyAction` mutates the `ScheduledDose` (status/completedAt/snoozedUntil), appends a `DoseEvent`, saves the context → `AppDependencies.refreshSchedules` regenerates (rolling re-anchor), reschedules notifications and republishes the widget. When editing this flow, all three steps (repository mutation, event log, notification reschedule) need to stay together. **Snooze** only applies once a dose is due (`DoseActions.canSnooze`: due/overdue/snoozed, and the policy's `allowSnooze`): snoozing an upcoming dose made the snooze end its new window start, pulling it *earlier*; `applyAction` refuses it (no event) and `DoseActionBar` hides the button (`onSnooze: nil`). A snooze still shifts both window bounds (unchanged design: a snoozed morning dose stays "on time" for the window's length after the snooze). `MedicationScheduledDosesView` offers actions only on due/overdue/snoozed doses and the next upcoming one (early doses stay possible); the rest of the 90 days is a preview.

- **Design system (`Support/DesignSystem/`)**: `Theme` is the design-token namespace — `Theme.Spacing`/`Theme.Radius`/`Theme.Font` (SF Pro Rounded for display text) in `Theme.swift`, and `Theme.Color` in `Theme+Color.swift`, a typed facade over `Assets.xcassets/Theme/*.colorset` (each with Any + Dark appearance variants, converted from the source design's OKLCH values). Never call `Color("...")` outside that facade. `DoseStatus+Theme.swift` is the single source of truth for status → color/SF-Symbol mapping (`themeColor`/`themeSoftColor`/`symbolName`). High-contrast support is border-width-only, via the `themedBorder`/`themedCapsuleBorder` helpers reading `@Environment(\.colorSchemeContrast)` — there is no third color axis.

- **Shared components (`Shared/Components/`)**: reusable, presentational SwiftUI views — `DoseCard` (the primary dose card: artwork + status pill + action bar + supply row), `StatusPill`, `ActionButton`/`DoseActionBar` (Take/Snooze/Skip, goes vertical at accessibility type sizes), `SupplyRow`, `SimpleDoseRow`, `ComingUpRow`, `SectionHeader`, `DateGroupLabel`, `Toast` (+ `.toast(_:)` modifier), `MedicationArtworkView` (photo, or a letter avatar tinted by `Medication.avatarHue`). Convention: components take pre-resolved data (`DoseStatus`, quantities) and closures — never `@Environment(\.appDependencies)` — so screens keep owning `recordDoseAction` calls and components stay previewable in isolation. Interactive components thread `AccessibilityID` identifiers through parameters.

- **Features (`Features/`)**: one folder per screen area (`Today`, `Medications`, `History`, `Settings`), each a SwiftUI view (or view + subviews) that reads from `@Environment(\.appDependencies)` / SwiftData `@Query`s and calls back into `AppDependencies`. `TodayView` (inside a `TimelineView(.everyMinute)` so statuses flip on screen as windows open and close) renders time-bucketed sections (Overdue / Take Now / Coming Up Soon / Later Today / Tonight / Completed, plus a long-range per-medication "Coming Up" list); the bucketing rules live in `Features/Today/TodayBucketing.swift` as pure static functions (status resolution is injected as a closure) so they're unit-testable without SwiftData or a clock. Bucketing skips rows of archived medications and **superseded** misses: `DoseSupersession` (same file) treats an unresolved dose from an earlier day as replaced once that medication has another dose scheduled today — yesterday's missed daily pill is history, not a "Take" button next to today's (a weekly med missed yesterday stays overdue). The status is still `.overdue` (adherence counts it); Today, the medication list, the scheduled-doses list, notifications and the widget all hide it. Calendar mode lists every dose of active medications, taken and skipped ones included (it used to drop them, so past days were empty and today's taken doses vanished); `DoseCalendarView` reloads the decorations of days that lost their last dose and only pages when the selection moves to another month. Toasts are announced to VoiceOver; "Coming Up" rows show only the time (the group header names the day).

- **Supply tracking (container-based)**: `Medication` models on-hand supply as `supplyContainers: [Int]?` — an ordered list of remaining-counts per physical container (vial/bottle), where `totalRemaining` is the sum and `currentContainerRemaining` is the first non-empty element. `unitsPerContainer` is the container size (4 doses/vial, 90 tablets/bottle); `supplyUnitLabel`/`supplyLowThreshold`/`lastRefilledAt` round it out. Mutation lives on the model: `consumeOneUnit()` (draws down the open container, dropping it at 0 so the next opens), `restoreOneUnit()` (Undo), `addRefill(quantity:)` (appends a container — an early refill stacks behind the one still in use). `DoseRepository.applyAction` calls consume on `.taken`/restore on `.pending`; `MedicationRepository.logRefill` appends a container and logs a `RefillEvent`. Tracking is "on" iff `supplyUnitLabel` is non-empty. `MedicationKind.containerNoun` gives the "bottle"/"vial" wording. Threshold logic is a plain comparison (`isSupplyLow`). Supply tracking with an empty unit falls back to "doses"/"tablets" by kind (an empty unit used to switch tracking off silently). `SupplyRow.unit` singularizes ("1 dose left"). `SupplyContainerTests` covers the container math.

- **Notifications & "with food"**: `Medication.takeWithFood` surfaces on `DoseCard` and appends to the notification body. `NotificationScheduler` sets `interruptionLevel = .timeSensitive` per `Medication.timeSensitiveNotifications` (nil = inherit `AppPreferences.timeSensitiveByDefault`) so important reminders can break through Focus/DND — this needs the **Time Sensitive Notifications** capability, wired via `ShotTracker/ShotTracker.entitlements` (`com.apple.developer.usernotifications.time-sensitive`). There are no quiet hours (removed); `TimingAnchorKind` is time-only (`morning`/`noon`/`evening`/`night`/`bedtime`/`exactTime`) — the meal-relative anchors were replaced by the `takeWithFood` flag.

- **Medication detail flow**: `MedicationDetailView` is a compact summary (artwork, schedule, supply + "Log refill") with `NavigationLink`s into `MedicationScheduledDosesView` and `MedicationHistoryDetailView` (the latter interleaves `DoseEvent`s and `RefillEvent`s). `DoseEventRow` (in `Shared/Components/`) is shared by the global History tab and the per-med history.

- **Medication lookup & Add Medication modes**: `EditMedicationView` shows a Lookup/Manual segmented switch (Lookup default) when adding a new medication (`medication == nil`); editing an existing one always uses the plain manual form — no switch. `MedicationLookupService` (`Services/MedicationLookup/`) hits the free NIH RxTerms API (`clinicaltables.nlm.nih.gov`) and returns one `MedicationLookupResult` per drug+route group, each carrying `variants: [MedicationVariant]` (a specific strength/form + its own RxCUI, e.g. "500 mg Tab") — `parseVariants` zips RxTerms' parallel `STRENGTHS_AND_FORMS`/`RXCUIS` arrays and is unit-tested independent of the network call. `Features/Medications/MedicationLookupFlow.swift` renders the search list and a pushed strength-picker (`MedicationVariantPickerView`); a single-variant result confirms immediately instead of pushing a picker for one row. Confirming a variant sets `Medication.selectedStrengthAndForm` (display string) and points `normalizedMedicationCode` at the variant-level RxCUI (more precise than the old group-level code), then kicks off `DrugInfoService.fetchLabel` in the background — never blocking Save.

- **Drug info (`Services/MedicationLookup/DrugInfoService.swift`)**: a stateless enum (same shape as `DoseForecastService` — no DI wiring) that queries the free openFDA Drug Label API (`api.fda.gov/drug/label.json`, no auth needed at this app's volume) by `openfda.rxcui` first, falling back to `openfda.generic_name`. Returns `DrugLabelInfo?` — full label sections (description, warnings, boxed warning, indications & usage, adverse reactions), always optional since openFDA coverage varies per drug and a miss must never block adding a medication. **Field naming gotcha**: SwiftData/Core Data reject any `@Model` or embedded-Codable-struct property literally named `description` (collides with `NSObject.description`) — the app crashes at container-init with "Unable to have an Attribute named description" if that's ever reintroduced; `DrugLabelInfo` uses `drugDescription` instead. Surfaced via a "Drug Info" row in `MedicationDetailView` (shown only when `DrugLabelInfo.hasContent`) linking to `MedicationDrugInfoView`, which also has a manual "Refresh" action.

- **Deleting a medication is a soft-delete**: `MedicationRepository.archive(_:in:)` sets `Medication.isActive = false` rather than calling `context.delete` — dose/refill history (`DoseEvent`, `RefillEvent`) is never touched, so it keeps showing up in `MedicationHistoryView`/`MedicationHistoryDetailView` after "deletion." It does prune the medication's *unresolved* `ScheduledDose` rows (first detaching their `DoseEvent`s — `ScheduledDose.events` cascades, so a snoozed or undone dose used to take its logged events with it) (anything not `.takenOnTime`/`.takenLate`/`.skipped`) — necessary because `DoseRepository.refreshSchedules`'s per-medication loop is gated on `isActive`, so once a medication goes inactive its rows are never touched (generated *or* pruned) again; without this explicit one-time cleanup, stale future doses and their notifications would linger forever. `MedicationListView` and `TodayView`'s `@Query`s both filter `#Predicate<Medication> { $0.isActive }` so archived medications disappear from the active list, Today, and Coming Up. Both `MedicationListView` (swipe-to-delete) and `MedicationDetailView` ("Delete Medication" button) gate the archive behind a confirmation `.alert`. There's currently no UI to reactivate or permanently purge an archived medication.

- **Home-screen widget (`ShotTrackerWidgetExtension` target, `ShotTrackerWidget/` folder)**: a WidgetKit extension (small/medium/large, `StaticConfiguration`, non-interactive — tap opens the app) showing today's doses, **overdue first then upcoming-today**. A widget runs in its own process and can't read the SwiftData store, so the pattern is a **snapshot, not shared persistence**: the app writes a small Codable projection to an **App Group** (`group.bedar.net.ShotTracker`, in both `ShotTracker.entitlements` and `ShotTrackerWidget/ShotTrackerWidget.entitlements`) and the widget renders from it — the live `default.store` is never relocated or opened by the widget. `Services/Widget/WidgetSnapshotWriter.write(context:evaluator:preferences:)` fetches `ScheduledDose`s, runs them through the *same* `TodayBucketing.bucket(...)` used by TodayView, keeps `overdue + takeNow + comingUpSoon + laterToday + tonight` (drops completed + long-range), **appends tomorrow's unresolved doses** (so the widget is right after midnight without the app being opened — it used to show yesterday's leftovers, then nothing), maps to `WidgetDoseItem` (now with `medicationID`, optional for old snapshots), writes `today-snapshot.json` atomically, and calls `WidgetCenter.shared.reloadAllTimelines()`. It's invoked from all three `AppDependencies` mutation points (`bootstrapIfNeeded`/`refreshSchedules`/`recordDoseAction`, via `refreshWidgetSnapshot(context:)`) and when the names-visibility setting toggles. The shared type `Shared/Widget/TodayWidgetSnapshot.swift` is compiled into **both** targets (app via its fsync group; widget via an explicit `PBXBuildFile` reference to the same path) and is deliberately self-contained — no SwiftData, no `@Model`, no Theme asset catalog — so it defines its own `WidgetDoseStatus` (raw-value-identical to `DoseStatus`) and a `resolvedStatus(now:)` that **mirrors `DoseStatusEvaluator.effectiveStatus` line-for-line** (the widget re-resolves status at each timeline entry so doses flip upcoming→due→overdue without an app write). `TodayWidgetSnapshot.items(relevantAt:)` mirrors `DoseSupersession` and hides later days' items; the provider's timeline covers today and tomorrow plus midnight. `WidgetStatusParityTests` guards that mirror against drift; keep the two in sync. The widget styles status with its own `WidgetStatusStyle` (semantic colors + SF Symbols matching `DoseStatus+Theme`), not the Theme facade. A **Settings toggle** `AppPreferences.showMedicationNamesInWidget` (default on) drives a discreet mode (kind icon + time + status, no names) for home-screen privacy. Deep link: the widget's `.widgetURL(shottracker://today)` is handled by `AppRootView.onOpenURL` selecting the Today tab. **Widget target gotchas**: it uses a physical `Info.plist` (partial — `NSExtension`/`NSExtensionPointIdentifier = com.apple.widgetkit-extension`, merged with generated keys via `GENERATE_INFOPLIST_FILE = YES` + `INFOPLIST_FILE`), and its fsync group carries a `membershipExceptions` for `Info.plist`/`ShotTrackerWidget.entitlements` so they aren't double-copied into Copy Resources. The App Group works on the simulator without portal provisioning; a device/TestFlight build needs Xcode signed into team `LMNQ9YTY2C` to register the group.

- **Notification actions**: dose reminders carry the `DOSE_REMINDER` category (Take/Snooze/Skip buttons on the banner). `NotificationActionHandler` (`Services/Notifications/`) is the `UNUserNotificationCenterDelegate` — wired in `ShotTrackerApp.init` (delegate is held weakly; the app struct keeps the instance alive) — and routes an action back to `AppDependencies.recordDoseAction` by fetching the dose via the `occurrenceKey` in `userInfo`. A plain tap just opens the app. `willPresent` keeps banners visible in the foreground.

- **Refill forecasting (`Services/Scheduling/SupplyForecastService.swift`)**: projects a supply-tracked medication's run-out date by counting future doses against `totalRemaining`: the persisted doses still to come (they know what was already taken or skipped today — the stateless forecast counted a dose taken this morning a second time), then `DoseForecastService` occurrences after the last persisted one (a dose whose window already closed doesn't count). `AppDependencies.logRefill` refreshes the refill reminder and widget after a refill. Surfaces as a "Runs out Jul 28 (~12 days)" line on `SupplyRow` (optional `forecastText`) and as a per-medication refill reminder notification (id `refill-{medID}`, fired at 10:00 local `refillReminderLeadDays` (3) before run-out) scheduled from `NotificationScheduler.rescheduleAll` — which now takes the engine as a parameter for this. `SupplyForecastServiceTests` covers the math.

- **History tab** (`Features/History/MedicationHistoryView.swift`): per-medication filter chips (archived meds included — their history is the point), month-grouped sections, an **adherence insights card** (30-day % / dosing-day streak / most-missed slot, computed by the pure `Services/Scheduling/AdherenceStats.swift` from persisted `ScheduledDose` rows with status injected — `AdherenceStatsTests`), and a toolbar **CSV export** (`Services/Export/HistoryCSVExporter.swift`, RFC-4180 escaping, dose + refill events newest-first, shared via `ShareLink`/`Transferable` as `ShotTracker-History.csv` — `HistoryCSVExporterTests`).

- **Editing a medication** (`EditMedicationView.saveMedication`): a new regimen version is created only when `MedicationDraft.scheduleDiffers(from:)` (start day, recurrence, timings, grace, missed-dose policy, minimum interval, phases); changed reminder settings append a newer `ReminderPolicy` to the current regimen instead (`activeReminderPolicy` is the newest). Renaming a med or editing its notes used to bump the version and re-key every future dose. The form keeps at least one weekday and one time, defaults weekly/monthly to today's weekday/date, shows the grace stepper only for specific-time doses, and dropped the dead "Routine slot window" stepper (`routineSlotReminderWindowMinutes` is stored but unused). Photos are stored as ≤ 600 px JPEGs (`Support/PhotoDownscaler.swift`). Lookup search is debounced (300 ms) and ignores cancelled requests (they used to flash "Search is unavailable" on every keystroke); `MedicationLookupResponse` tolerates a `null` extras element. History and the CSV show undo events as "Undone" (`DoseActionType.historyTitle`); the History filter chips are a list row (as a top inset they hid the navigation title).

- **Settings**: a permission row says whether reminders can arrive (allowed / turned off → "Open Notification Settings" / "Allow Notifications"); `NotificationScheduler` is `@Observable` for it.

- **Archived medications**: `MedicationRepository.unarchive` + `ArchivedMedicationsView` (reachable from an "Archived (N)" row at the bottom of the Medications list) restore an archived med; callers must `refreshSchedules` after so doses regenerate.

- **Onboarding**: there is **no seeded sample medication** (the old `seedIfNeeded` "Weekly Shot" was removed). A fresh install shows guided empty states — the Medications tab's welcome `ContentUnavailableView` has an "Add your first medication" action. Notification permission is primed in `EditMedicationView.saveMedication` right after a save when status is `.notDetermined` (the moment a schedule needing reminders first exists).

- **HealthKit medications (investigated, not built)**: the iOS 26 HealthKit medication APIs (`HKMedicationDoseEvent`, `HKUserAnnotatedMedication`) are **read-only for third-party apps** — every initializer is `NS_UNAVAILABLE` and all properties readonly, so exporting dose logs into Apple Health is not possible. Only a read/import direction (mirroring the user's Health-app med list) is viable if ever wanted.

## Conventions

- Status, frequency, timing, and kind are modeled as exhaustive `String`-backed enums (`DoseStatus`, `DoseActionType`, `ScheduleFrequency`, `TimingAnchorKind`, `MedicationKind`) in `MedicationModels.swift` rather than free-form strings or booleans — extend these enums (and their `title` switch statements) rather than adding parallel flags.
- Colors, spacing, radii, and fonts come from the `Theme` namespace (`Support/DesignSystem/`), never hardcoded values or direct `Color("...")` asset lookups; status colors come from `DoseStatus.themeColor`/`.themeSoftColor` only.
- New `Medication`/`ScheduledDose` stored properties must be optional (or have an in-declaration default) — the app relies on SwiftData's automatic lightweight migration with no versioned schema plan, which only handles additive changes. New `@Model` types must also be registered in `MedicationModelContainer.makeSharedContainer()`'s `Schema`.
- Verify any data-model change by launching over a simulator that already has app data (install without uninstalling first) to confirm lightweight migration doesn't crash — not just against a fresh install.
- Repositories are `@MainActor enum`s of `static` functions that take `ModelContext` explicitly as a parameter — there are no repository instances or protocols.
- Regimens are versioned (`MedicationRegimen.version`); schedule changes should create a new version rather than mutating occurrence generation for existing `ScheduledDose`s in place, since `occurrenceKey` embeds the version.

**Still open**
- Notifications are only re-planned when the app runs (launch, foreground, an action, a notification action). With several medications the 64-request budget covers a few days; a `BGAppRefreshTask` that re-plans daily would close the gap.
- Regimens keep the time zone they were created in: after a move, "Morning" stays 6–12 at home time. Whether named slots should follow the device's zone (and exact times stay put) is a product decision.
- A snooze shifts the whole window (a morning dose snoozed at 10:00 stays "on time" until ~16:20). Unchanged; arguably it should only delay the reminder.
- Widget and notification-action paths aren't covered by UI tests (WidgetKit and notification banners can't be driven from XCUITest here); their logic is unit-tested (`NotificationPlanner`, `TodayWidgetSnapshot.items(relevantAt:)`, `WidgetSnapshotWriter`).
- Tab bar button identifiers can't be set (see Commands); tests find tabs by title.
